# Spec — Duplicate task (2026-09-13)

Exercise: **Write a Specification** (lesson: Why Specifications Matter).
Feature: a **Duplicate** action on a task row that creates an active copy of the task
directly below the original. Small on purpose: no model change, no new endpoint, same
behaviour in both storage modes.

Status: draft for peer read. Not implemented. Where this file conflicts with `SPEC.md`,
`SPEC.md` wins.

---

## 1. Functional requirements

FR1. Each task row offers a **Duplicate** action next to the existing Edit and Delete
     icon buttons. It is a real `<button>` labelled "Duplicate task".
FR2. With the roving focus on a row, **Shift+D** triggers the same action. The check is
     on `event.shiftKey`, not on letter case, so CapsLock+D still toggles done and only
     a held Shift duplicates.
FR3. Duplicating creates **one new task** with these fields copied verbatim from the
     source: `title`, `notes`, `priority`, `dueDate`, `tagIds`, `parentId`.
FR4. The copy is always **active**: `completedAt` is `null` even when the source is done.
FR5. The copy gets a fresh client-minted UUIDv4 `id`; `createdAt` and `updatedAt` are the
     time of duplication.
FR6. The copy appears **immediately below the source** in the full position-ordered
     list (all tasks, not the filtered view, so a hidden task between the source and its
     visible neighbour still counts). Tasks below the source shift down by one row;
     nothing else moves.
FR7. The action is optimistic like every other store mutation: the copy shows at once;
     if the adapter rejects the write, the copy disappears and an error toast is shown.
FR8. Duplicate works identically in `local` and `api` storage modes and produces a task
     the other mode would accept unchanged (same envelope shape, same validation rules).
FR9. Duplicating a task that is hidden by the current filter (e.g. copying a completed
     task while the Active filter is on) still creates the copy; the copy is visible
     whenever the source would be visible as an active task.

## 2. Acceptance criteria (GIVEN / WHEN / THEN)

Each criterion names the test file that would pin it (see §6 for the mapping).

AC1  **Copy fields.** GIVEN task S = {title:"Ship tokens", notes:"see Figma",
     priority:"HIGH", dueDate:"2026-09-20", completedAt:"2026-09-10T08:00:00.000Z",
     tagIds:[T1], parentId:null}, WHEN the user duplicates S, THEN the system shall
     create task C with title, notes, priority, dueDate, tagIds, parentId equal to S's,
     `completedAt` = null, `id` ≠ S.id, `createdAt` = `updatedAt` = now.

AC2  **Position with a gap.** GIVEN ordered tasks A(1024) S(2048) B(3072), WHEN the user
     duplicates S, THEN C.position shall be 2560 and no other task's position changes.

AC3  **Position at the end.** GIVEN ordered tasks A(1024) S(2048) and S is last, WHEN the
     user duplicates S, THEN C.position shall be 3072 (S.position + 1024).

AC4  **Position with no gap.** GIVEN ordered tasks S(1024) B(1025) D(2049), WHEN the
     user duplicates S, THEN the system shall first renormalize the existing list to
     S=1024 B=2048 D=3072 via one `reorderTasks` batch, and THEN create C at 1536.
     The relative order S, C, B, D shall hold afterwards.

AC5  **Optimistic insert.** GIVEN S in the store, WHEN duplicate is invoked, THEN the
     copy shall be present in `tasks` before the adapter promise settles.

AC6  **Rollback on rejection.** GIVEN the adapter's `createTask` rejects with
     `RepositoryError('network')`, WHEN the user duplicates S, THEN the store's task
     list shall equal its pre-duplicate snapshot and one toast with `kind: 'error'`
     shall be pushed (the store's existing `pushError` convention: message comes from
     the `RepositoryError`, not a hard-coded string).

AC7  **Source vanished.** GIVEN S was deleted in another tab and the store has already
     reconciled (S is not in `tasks`), WHEN duplicate is invoked with S.id, THEN the
     action shall return `false`, call no adapter method, and change no state.

AC8  **Row button.** GIVEN a rendered row for S, WHEN the user clicks the button
     labelled "Duplicate task", THEN the store's `duplicateTask` shall be called once
     with S.id.

AC9  **Shortcut.** GIVEN the roving focus is on S's row and no input is focused, WHEN
     the user presses Shift+D, THEN `duplicateTask(S.id)` shall be called once and the
     event's default shall be prevented. WHEN the user presses `d` without Shift, THEN
     `toggleTask` shall be called and `duplicateTask` shall not.

AC10 **Both adapters accept the copy.** GIVEN the task C produced by AC2, WHEN
     `createTask(C)` is called on `LocalStorageAdapter` and on `ApiAdapter` (MSW),
     THEN both shall resolve with a task equal to C.

AC11 **Legacy key untouched.** GIVEN any duplicate in local mode, WHEN the write
     completes, THEN `localStorage['todo-app-items']` shall be byte-identical to
     before.

## 3. Input / output examples

Happy path — duplicate the middle task (matches AC1 + AC2). `now` = `2026-09-13T10:15:00.000Z`,
minted id = `7c9e6679-7425-40de-944b-e07fc1f90ae7`.

Before (`tasks`, position order):

```json
[
  {"id":"a1","title":"Vendor Inter font","position":1024, "...":"..."},
  {"id":"s1","title":"Ship tokens","notes":"see Figma","priority":"HIGH",
   "dueDate":"2026-09-20","completedAt":"2026-09-10T08:00:00.000Z","position":2048,
   "parentId":null,"tagIds":["t-work"],"createdAt":"2026-09-01T09:00:00.000Z",
   "updatedAt":"2026-09-10T08:00:00.000Z"},
  {"id":"b1","title":"Write README","position":3072, "...":"..."}
]
```

Adapter call issued (local: envelope write; api: `POST /api/v1/tasks`):

```json
{"id":"7c9e6679-7425-40de-944b-e07fc1f90ae7","title":"Ship tokens","notes":"see Figma",
 "priority":"HIGH","dueDate":"2026-09-20","completedAt":null,"position":2560,
 "parentId":null,"tagIds":["t-work"],
 "createdAt":"2026-09-13T10:15:00.000Z","updatedAt":"2026-09-13T10:15:00.000Z"}
```

After: `a1(1024) s1(2048) 7c9e…(2560) b1(3072)`. API mode returns `201` with
`Location: /api/v1/tasks/7c9e6679-7425-40de-944b-e07fc1f90ae7`.

Error case — network failure in API mode (matches AC6):

```
POST /api/v1/tasks  →  (fetch rejects: TypeError: Failed to fetch)
ApiAdapter throws RepositoryError { kind: "network", message: "Could not reach the server" }
```

Store afterwards: `tasks` = `[a1, s1, b1]` exactly as before; `toasts` gains
`{ kind: "error", message: "Could not reach the server" }` (the adapter's message, via
the store's `pushError`). Nothing was renormalized because the gap was already wide
enough.

Error case — no gap and the create fails (edge of AC4 + AC6): tasks `s1(1024) b1(1025)`.
The `reorderTasks([{s1,1024},{b1,2048}])` batch succeeds, then `createTask` rejects. End
state: `s1(1024) b1(2048)`, no copy. The numeric positions changed but the visible order
did not; this is accepted (see §4 C6).

## 4. Constraints

C1. **No domain-model change.** No new field, no change to any of the five layers
    (`types.ts`, migration, DTOs, entities, DDL). `/contract-check` must pass unchanged.
C2. **No new REST endpoint and no Flyway migration.** Duplicate is composed from the
    existing `StorageAdapter` methods `createTask` and, only when needed, `reorderTasks`.
    The backend is not touched.
C3. **Pure core.** Field copying and position choice live in one pure function in
    `frontend/src/domain/mutations.ts` that takes `newId` and `now` as arguments (the
    repo's test convention: never the wall clock, never fake timers).
C4. **Position math is reused, not re-implemented.** Use `midpoint`, `needsRenormalize`
    and `renormalize` from `domain/position.ts`; do not add a second gap algorithm.
C5. **Write count.** Common case = exactly one adapter write. Renormalize case = exactly
    two (`reorderTasks` then `createTask`), in that order.
C6. **Non-atomic renormalize is accepted.** In API mode the two writes are separate
    requests. If the second fails, the first stays. This is safe because renormalization
    is order-preserving and never changes which tasks exist. Note: both adapters bump
    `updatedAt` on every task in a `reorderTasks` batch (LocalStorageAdapter explicitly,
    the server via `@PreUpdate`), so on the no-gap path the source's `updatedAt` does
    change. That is existing reorder behaviour, not something this feature adds.
C7. **Validation is inherited.** The copy passes `domain/validation.ts` by construction
    (a valid source produces a valid copy). No new rule is added, so no Jakarta or
    CHECK constraint changes.
C8. **A11y.** Real button with a visible `:focus-visible` ring; the shortcut appears as a
    `<Kbd>` hint like the others; the copy's row receives roving focus after creation.
C9. **No new runtime dependency.**
C10. **Legacy boundaries.** Nothing under `legacy/` and the `todo-app-items` key are
    never read or written by this feature.

## 5. Out of scope

A reasonable reader might assume these are included. They are not.

O1. **Title suffix.** The copy's title is identical to the source; no " (copy)" or
    "Copy of". A suffix can overflow the 500-char limit and would need a strip rule on
    re-duplication. Decided against for v1.
O2. **Duplicating children.** If S has subtasks (rows with `parentId = S.id`), they are
    not copied. Subtask UI is cut in v1 (`SPEC.md` final decisions), so this cannot
    arise through the UI yet.
O3. **Bulk duplicate** of a multi-selection. There is no multi-select in v1.
O4. **Undo toast** for duplicate. Delete already exists and is itself undoable, so the
    copy is reversible without a dedicated undo.
O5. **Choosing the copy's position** (top of list, drag-to-place). Always directly below
    the source.
O6. **Duplicating tags.** Tag ids are referenced, not cloned. Deleting a tag later
    removes it from both source and copy, as with any two tasks sharing a tag.
O7. **A server-side endpoint** such as `POST /tasks/{id}/duplicate`. Additive later if a
    non-browser client needs it; the frontend contract would not change.
O8. **Copying `completedAt`.** A duplicated done task is active by design.
O9. **Cross-tab conflict handling** beyond the existing `storage`-event reconcile.

### 6.2 Which section felt forced?

**Out of scope**, and specifically O1 (title suffix). I wrote the whole first draft without
deciding whether the copy is called "Ship tokens" or "Ship tokens (copy)". Both are
defensible and a reader would pick either one silently. Forcing the section made the
decision; the peer read below is the check on whether it landed.

Constraints C5/C6 were the second soft spot: the renormalize path was hand-waved as
"just renormalize" until I had to write down which write goes first and what happens if
the second one fails. That produced the non-atomic accepted-risk note.

### 6.3 Error-case invariant

Chosen criterion: **AC6** (adapter rejects the create).

Invariant, one sentence: *For any duplicate attempt that does not complete, the set of
task ids and their relative order are identical before and after; the only permitted
persisted difference is the numeric position values written by an order-preserving
renormalization.*

Note what this invariant rules out: the store must not leave the optimistic copy behind,
must not have changed any field of S other than the position/`updatedAt` pair that an
order-preserving renormalize legitimately rewrites, and must not have appended the copy
at the end as a fallback. (First draft claimed "no `updatedAt` bump on S"; the peer read
showed both adapters already bump it on reorder, so the invariant was over-tight.)

## 7. Proposed shape (for the implementer, not binding)

```ts
// domain/mutations.ts
export interface DuplicateResult {
  task: Task
  renormalized?: { id: string; position: number }[] // present only on the no-gap path
}
export function duplicateTask(
  source: Task, ordered: readonly Task[], newId: string, now: string,
): DuplicateResult
```

Store action `duplicateTask(id): Promise<boolean>`: find source → compute →
(if renormalized: apply locally, `await adapter.reorderTasks`) → insert copy locally →
`await adapter.createTask(copy)` → on rejection restore snapshot + error toast.
